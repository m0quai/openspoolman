OpenSpoolMan / AMSHelper - offene BambuMqtt-Aufgabe fuer Codex
==============================================================
Stand: 25.08.2026

ZIEL
----
Die gestrige offene Aenderung an der Bambu-MQTT-Auswertung soll in Codex weitergefuehrt werden.
Der relevante aktuelle Code liegt unter:

  AMSHelper/Mqtt/BambuMqtt.cs
  AMSHelper/Mqtt/BambuStatusParser.cs
  AMSHelper/Mqtt/BambuStatusUpdate.cs

Die verbindlichen Projektregeln aus AGENTS.md sind dabei einzuhalten.

HINTERGRUND
-----------
Beim letzten Test wurde ueber FTPS auf dem P1S u. a. folgende Datei gefunden:

  ItsLitho_Kerstin.gcode.3mf

Es war offen, wie OpenSpoolMan/AMSHelper zuverlaessig weiss, WELCHE Datei gerade gedruckt wird.
Die Dateinamenslogik darf nicht einfach eine beliebige Datei vom FTPS-Verzeichnis nehmen.
Ausserdem darf nicht angenommen werden, dass die Druckdatei immer auf `.gcode.3mf` endet; sie kann je nach Quelle auch direkt als `.3mf` vorliegen.

AUFGABE FUER CODEX
------------------
1. Zuerst AGENTS.md vollstaendig lesen.
2. Aktuellen Branch und Working Tree pruefen.
3. BambuMqtt.cs, BambuStatusParser.cs und BambuStatusUpdate.cs vollstaendig lesen.
4. Die empfangenen Bambu-MQTT `/report`-Nachrichten darauf untersuchen, welches Feld bzw. welche Kombination von Feldern den aktuell laufenden Printjob bzw. dessen Dateinamen eindeutig liefert.
5. Nicht raten: Wenn der vorhandene Parser dieses Feld noch nicht kennt, anhand vorhandener Raw-/Debug-Ausgaben bzw. Bambu-Reportdaten verifizieren, welches Feld tatsaechlich gesendet wird.
6. Die Ermittlung des aktuellen Druckdateinamens in die bestehende Architektur integrieren:
   - BambuMqtt bleibt Transport/Subscribe/Empfang/Reconnect.
   - JSON-Auswertung bleibt in BambuStatusParser.
   - Der erkannte aktuelle Dateiname/Printjob-Zustand wird ueber BambuStatusUpdate bzw. eine passend gekapselte Statusstruktur weitergereicht.
7. Fehlende MQTT-Felder duerfen keinen alten/ungueltigen Dateinamen als neuen Wert vortaeuschen. Bestehendes Has...-Muster beibehalten bzw. entsprechend erweitern.
8. Falls fuer die nachgelagerte FTPS-Suche ein Dateiname normalisiert werden muss, beide Varianten beruecksichtigen:
   - `<name>.gcode.3mf`
   - `<name>.3mf`
   Keine globale Annahme, dass nur eine der beiden Formen vorkommt.
9. Keine Datei allein aufgrund ihres Namens oder Zeitstempels als aktuellen Job waehlen. Der Ausgangspunkt muss der tatsaechliche MQTT-Jobstatus des Druckers sein.
10. Debug-Ausgabe nur gezielt ergaenzen, damit beim Test sichtbar ist:
    - welches MQTT-Feld den Job/Dateinamen geliefert hat,
    - welcher Dateiname intern als aktuell gilt,
    - wann dieser Wert geaendert oder geleert wird.
11. Aenderungen mit Visual Studio / nanoFramework-kompatiblen Mitteln umsetzen und die Projektdateien mitpflegen, falls neue Dateien hinzukommen.
12. Nach Implementierung Diff pruefen und kurz dokumentieren, welches MQTT-Feld letztlich verwendet wird und warum.

WICHTIG
-------
Diese Datei ist eine Uebergabe der offenen Aufgabe und keine Behauptung ueber ein bestimmtes Bambu-MQTT-Feld. Codex soll das reale Feld im aktuellen Report/Code verifizieren, bevor die Implementierung festgelegt wird.
